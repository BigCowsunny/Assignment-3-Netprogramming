## สไลด์ 2 — ภาพรวมการทำงาน

เวลา 0:25–1:10 (45 วินาที)

ข้อความบนสไลด์:

- React + TypeScript แสดงผลบนเว็บ
- FastAPI ติดต่อ Router / Switch ผ่าน SNMPv2c
- SQLite เก็บอุปกรณ์ ทราฟฟิก และเหตุการณ์
- WebSocket ส่งเหตุการณ์และสถานะที่เปลี่ยน

คำพูด:

“ระบบแบ่งเป็นหน้าเว็บ บริการ Backend และฐานข้อมูล ผู้ใช้สั่งงานผ่าน React ส่วน FastAPI อ่านและสั่งงานอุปกรณ์ผ่าน SNMPv2c แล้วเก็บข้อมูลใน SQLite ถ้ามีเหตุการณ์หรือสถานะเปลี่ยน Backend จะส่งข้อความผ่าน WebSocket ให้หน้าเว็บ ส่วนกราฟย้อนหลังและความคืบหน้าของ Discovery ใช้ REST API อุปกรณ์จริงและ EVE-NG ใช้เส้นทางเดียวกัน โดยต้องมี Management IP ที่ Backend เข้าถึงได้ โปรแกรมไม่ได้อ่านข้อมูลจาก EVE-NG API ครับ”

## สไลด์ 4 — จัดการรายการอุปกรณ์

เวลา 1:50–2:35 (45 วินาที)

ข้อความบนสไลด์:

- เพิ่มด้วย IP, Community และ UDP port
- Test Connection และอ่าน IF-MIB ก่อนบันทึก
- ค้นหาและกรองตามประเภทหรือสถานะ
- แก้ไขการเชื่อมต่อ หรือลบออกจากระบบ

คำพูด:

“หน้าอุปกรณ์ใช้จัดการ Inventory ผู้ใช้เพิ่ม Management IP พร้อม Community และพอร์ต SNMP ซึ่งปกติเป็น UDP 161 กด Test Connection เพื่อตรวจการอ่านข้อมูล จากนั้นระบบต้องอ่านรายการ Interface จาก IF-MIB ได้ก่อนบันทึกเป็นอุปกรณ์ที่จัดการผ่าน SNMP นอกจากนี้ยังค้นหา กรอง แก้ไข และลบรายการได้ ถ้าพบอุปกรณ์จาก CDP หรือ LLDP แต่ยังไม่ยืนยัน SNMP ระบบจะแยกเป็นรายการที่พบและปิดการ Config ไว้ครับ”

## สไลด์ 5 — รายละเอียดอุปกรณ์และพอร์ต

เวลา 2:35–3:20 (45 วินาที)

ข้อความบนสไลด์:

- แสดงชื่อ รุ่น IP และ Uptime
- ดูรายการพอร์ตและภาพแสดงพอร์ต
- แยก Admin Status กับ Oper Status
- เลือกพอร์ตเพื่อดู Traffic หรือสั่งงาน

คำพูด:

“เมื่อคลิกชื่ออุปกรณ์ ระบบจะแสดงรายละเอียดและพอร์ตที่อ่านได้จาก SNMP จุดสำคัญคือ Admin Status เป็นค่าที่ตั้งให้เปิดหรือปิดพอร์ต ส่วน Oper Status เป็นสถานะลิงก์จริง เช่น Admin up แต่ Oper down หมายถึงสั่งเปิดแล้ว แต่สายหรือพอร์ตปลายทางยังไม่พร้อม เราจึงต้องอ่านสองค่านี้ร่วมกัน สำหรับรายการที่พบผ่าน CDP หรือ LLDP อย่างเดียว หน้านี้รู้เฉพาะพอร์ตที่เพื่อนบ้านประกาศ ไม่ใช่พอร์ตทั้งหมดของอุปกรณ์ครับ”

## สไลด์ 6 — เปิด–ปิดพอร์ตด้วย SNMP SET

เวลา 3:20–4:10 (50 วินาที)

ข้อความบนสไลด์:

- เลือก Interface และยืนยันคำสั่ง Up / Down
- ส่ง ifAdminStatus ค่า 1 = up หรือ 2 = down
- อ่านค่ากลับเพื่อยืนยันผลจากอุปกรณ์
- บันทึก Audit และแจ้งหน้าเว็บผ่าน WebSocket

เงื่อนไขที่แสดงบนสไลด์: ต้องมีสิทธิ์เขียน OID ของพอร์ต และ Admin up ยังไม่รับรองว่า Oper up

คำพูด:

“ฟังก์ชันนี้ควบคุมการเปิดใช้งาน Interface ด้วย SNMP SET ระบบส่ง ifAdminStatus ตาม ifIndex ของพอร์ต โดย 1 คือเปิดและ 2 คือปิด จากนั้น GET อ่านค่ากลับก่อนบันทึกผล พร้อม Audit log และข้อความ PORT_STATUS_CHANGE ผู้ใช้ต้องมี Community ที่ได้รับสิทธิ์เขียน OID นี้ การทดสอบอ่าน SNMP สำเร็จจึงยังไม่ยืนยันว่าสั่ง SET ได้ และเปิด Admin สำเร็จก็ยังต้องตรวจ Oper Status ของลิงก์ครับ”

## สไลด์ 7 — Traffic รับ–ส่งและกราฟย้อนหลัง

เวลา 4:10–5:00 (50 วินาที)

ภาพกราฟบนสไลด์เป็นข้อมูล Live จริงของ R1 Ethernet0/0 ที่แคปเมื่อ 7 ตุลาคม 2026 ประมาณ 10:36 น. มี In/Out ราว 2 Kbps ค่าหน้าเว็บอาจเปลี่ยนตามช่วงเวลาและทราฟฟิกใน Lab

ข้อความบนสไลด์:

- อ่าน Octet counters แล้วคำนวณอัตรา In / Out เป็น bps
- เลือกช่วง Live, วัน, สัปดาห์, เดือน หรือปี
- ดูค่าปัจจุบัน ต่ำสุด สูงสุด และเฉลี่ย
- ส่งออกข้อมูล CSV หรือรูปกราฟ PNG

เงื่อนไขที่แสดงบนสไลด์: เริ่มคำนวณเมื่อมี counter อย่างน้อย 2 รอบ และแสดงย้อนหลังเท่าที่เก็บจริง

คำพูด:

“กราฟใช้ตัวนับ Octets จากอุปกรณ์จริง ระบบนำค่าที่เพิ่มขึ้นคูณ 8 และหารด้วยเวลาระหว่างการอ่าน เพื่อแปลงเป็นบิตต่อวินาที จึงต้องอ่านอย่างน้อยสองรอบก่อนมีอัตราทราฟฟิก โค้ดปัจจุบันใช้ Counter 64 บิตเมื่ออ่านได้ และรองรับ 32 บิตเป็นทางเลือก พร้อมตรวจการรีบูตหรือ Counter reset เพื่อเริ่มค่าฐานใหม่ ผู้ใช้เลือกช่วงเวลา ดูสถิติ และส่งออก CSV หรือ PNG ได้ การเลือกช่วงหนึ่งปีไม่ได้แปลว่ามีข้อมูลย้อนหลังครบหนึ่งปี ข้อมูลขึ้นกับระยะเวลาที่ระบบเก็บจริงครับ”

## สไลด์ 8 — เหตุการณ์ Link Up / Link Down

เวลา 5:00–5:45 (45 วินาที)

ข้อความบนสไลด์:

- รับ SNMP Trap จากอุปกรณ์ผ่าน UDP
- จับคู่ Source IP และ ifIndex กับพอร์ต
- เก็บเหตุการณ์และส่ง TRAP_EVENT ผ่าน WebSocket
- ค้นหาและกรองเหตุการณ์ตามอุปกรณ์หรือประเภท

ภาพประกอบเป็นประวัติ 14 เหตุการณ์ที่บันทึกไว้ โดย Source ไม่ตรงกับ R1 ที่อ่าน SNMP อยู่ในรอบนี้ ยังไม่พบ Trap ใหม่จาก R1 ระหว่างการแคป Backend ฟัง UDP 162 และ IP ฝั่ง VMnet8 คือ 192.168.213.1

เงื่อนไขการใช้งาน: อุปกรณ์ต้องตั้งปลายทาง Trap ให้ถึง Backend

คำพูด:

“Polling เป็นการอ่านตามรอบ ส่วน Trap เป็นแพ็กเก็ตที่อุปกรณ์ส่งมาเมื่อเกิดเหตุการณ์ Receiver รองรับ Link Up และ Link Down แล้วจับคู่ IP และ ifIndex เพื่ออัปเดตพอร์ต เก็บเหตุการณ์ใน SQLite และส่งให้หน้าเว็บ ผู้ใช้ค้นหา กรอง หรือพักการแสดงผลสดได้ โดย Receiver ยังรับแพ็กเก็ตต่อเนื่อง ระบบไม่สร้าง Trap ปลอมจากการ Poll หรือกด SET ปุ่มทดสอบส่งแพ็กเก็ต UDP จริงที่ระบุ TestInterface ซึ่งใช้ตรวจบริการ แต่ยังไม่ใช่หลักฐานว่า Router จริงตั้งปลายทาง Trap ถูกต้องครับ”

## สไลด์ 9 — Auto Discovery ด้วย CDP / LLDP

เวลา 5:45–6:40 (55 วินาที)

ข้อความบนสไลด์:

- เริ่มจาก Seed IP หรืออุปกรณ์ที่บันทึกไว้
- อ่าน Neighbor ผ่าน SNMP แล้วค้นต่อจาก IP ที่พบ
- รับประกาศ CDP / LLDP ที่มาถึง NIC ของ Backend
- แสดงอุปกรณ์ไม่มี IP และยืนยัน SNMP ภายหลังได้

ภาพผลค้นหาจริง: Seed 192.168.213.131 ตรวจ 2 nodes และพบ 1 Neighbor link

เงื่อนไขที่แสดงบนสไลด์: อุปกรณ์ไม่มี IP หรือยังไม่ยืนยัน SNMP ใช้ Config และ Traffic ไม่ได้

คำพูด:

“Discovery มีทั้งการอ่าน Neighbor table ผ่าน SNMP และการรับประกาศ CDP หรือ LLDP จากเครือข่าย การค้นแบบ Active เริ่มจาก Seed IP หรืออุปกรณ์ที่ระบบรู้จัก แล้วค้นต่อเมื่อ Neighbor มี IP จึงไม่จำเป็นต้องระบุ Subnet ทุกครั้ง ส่วนการรับแบบ Passive เห็นเฉพาะเฟรมที่มาถึง NIC ของ Backend และบน Windows ต้องมี Npcap รายการไม่มี IP ยังแสดงชื่อ รุ่น และพอร์ตที่ประกาศได้ แต่ยังอ่านทราฟฟิกหรือสั่งงานไม่ได้ เมื่อมี Management IP แล้ว ผู้ใช้ตั้งค่าและยืนยัน SNMP เพื่อจัดการต่อ โดยคงตัวตนและสายเดิมครับ”

## สไลด์ 10 — Topology แสดงความสัมพันธ์ของอุปกรณ์

เวลา 6:40–7:25 (45 วินาที)

ข้อความบนสไลด์:

- สร้าง Node และสายจาก CDP / LLDP Neighbor
- แสดงชื่อพอร์ตทั้งสองฝั่งและลดรายงานซ้ำ
- ลากจัดตำแหน่งและคลิก Node ดูรายละเอียด
- อัปเดตข้อมูลเมื่อค้นหาใหม่หรือข้อมูลหมดอายุ

ภาพแผนที่จริงแสดง R1.localdomain Et0/0 ↔ Router.localdomain Ethernet0/0 โดย R1 .131 ยืนยัน SNMP แล้ว ส่วน Router .132 ยังเป็น Discovered only

เงื่อนไขที่แสดงบนสไลด์: Topology อ้างอิง Neighbor ที่อุปกรณ์รายงาน และอาจเห็นได้ไม่ครบทุกสาย

คำพูด:

“Topology นำข้อมูล Neighbor มาสร้าง Node และสาย พร้อมชื่อพอร์ตต้นทางและปลายทาง ระบบรวมรายงานซ้ำ เช่น ชื่อพอร์ตแบบย่อและแบบเต็ม หรือรายงานเดียวกันจาก CDP และ LLDP ผู้ใช้ลากจัดตำแหน่งและคลิก Node เพื่อเปิดรายละเอียดได้ ในบางกรณีมีหลายอุปกรณ์ใช้พอร์ตเดียวกัน ระบบจัดภาพเป็นจุดเครือข่ายร่วมเพื่อให้อ่านง่าย ความครบขึ้นกับข้อมูล Neighbor ที่อ่านได้ ภาพนี้ไม่ได้อ้างว่ารู้สายทั้งหมดจาก EVE-NG และระบบไม่ได้เดาสายเพียงเพราะ IP อยู่ Subnet เดียวกันครับ”

## สไลด์ 11 — ตั้งค่าระบบและตรวจสอบ Audit

เวลา 7:25–8:05 (40 วินาที)

ข้อความบนสไลด์:

- ปรับรอบ SNMP Polling ได้ 10–3,600 วินาที
- เก็บค่าตั้งไว้และใช้หลังรีสตาร์ตระบบ
- ตรวจสถานะ API, Poller และพอร์ต Trap Receiver
- ค้นหาประวัติคำสั่งและผลการดำเนินการ

คำพูด:

## คำถามที่อาจพบ

**Polling ต่างจาก Trap อย่างไร?**

Polling คือ Backend ขออ่านข้อมูลตามรอบ ส่วน Trap คืออุปกรณ์ส่งแพ็กเก็ตแจ้งเหตุการณ์มายัง Receiver ระบบส่ง Trap ที่รับได้ให้หน้าเว็บผ่าน WebSocket

**Admin up แต่ Oper down หมายถึงอะไร?**

ตั้งให้เปิดใช้งานพอร์ตแล้ว แต่ลิงก์จริงยังไม่พร้อม เช่น สายหรือพอร์ตอีกฝั่งมีปัญหา

**Test Connection สำเร็จแล้วสั่ง Up/Down ไม่ได้เพราะอะไร?**

GET สำเร็จยืนยันสิทธิ์อ่าน แต่ SET ต้องมีสิทธิ์เขียน ifAdminStatus ด้วย รวมถึงต้องได้รับอนุญาตจากการตั้งค่าอุปกรณ์

**คำนวณ Traffic อย่างไร?**

อัตรา bps = (Octets รอบใหม่ − Octets รอบก่อน) × 8 ÷ เวลาระหว่างรอบ ระบบตรวจ Counter width, reboot และ discontinuity ก่อนใช้ผล

**ค้นหาอุปกรณ์ที่ไม่มี IP ได้อย่างไร?**

ใช้ข้อมูล Neighbor จาก CDP/LLDP ผ่านอุปกรณ์ที่อ่าน SNMP ได้ หรือจากเฟรมที่มาถึง NIC ข้อมูลนี้บอกตัวตนและพอร์ตที่ประกาศ แต่ยังไม่ใช่การเข้าถึงอุปกรณ์เพื่อ Monitor ทุกพอร์ต

**เชื่อม EVE-NG ผ่าน API หรือไม่?**

โปรแกรมใช้ SNMP กับ IP ของ Node และใช้ CDP/LLDP เพื่ออ่าน Neighbor ไม่ได้เรียก EVE-NG API

**รองรับ SNMP เวอร์ชันใด?**

Monitoring GET/WALK/SET ในโค้ดปัจจุบันใช้ SNMPv2c ส่วน Link Trap Receiver ถอดแพ็กเก็ต v1/v2c ได้ ยังไม่มี SNMPv3 สำหรับ Monitoring

**ข้อมูลช่วงปีคือมีครบ 365 วันทันทีหรือไม่?**

เป็นตัวเลือกช่วง Query กราฟ แสดงเฉพาะ Sample ที่ระบบเก็บจริง

**Audit log มีระบบ Login แล้วหรือยัง?**

ยังไม่มีระบบ Login และ Role ชื่อ admin ที่บันทึกไม่ใช่หลักฐานการยืนยันตัวตน
